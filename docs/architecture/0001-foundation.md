# 0001 使用 Vben 与 Nunu 构建轻量业务脚手架

日期：2026-11-13。状态：技术底座已确定，业务功能待实现。

## 背景与决策

目标是保留若依式字典和代码生成闭环，同时让业务状态在 Go 代码中显式可读、便于 AI 定位和修改，并能持续调整前端视觉。

采用 Vben Admin 作为前端框架、Nunu Basic 作为后端源码起点，以 `frontend/`、`backend/` 组成单仓库。后端采用 Gin + GORM 的模块化单体及 REST 接口；配置和日志优先复用 Nunu 的 Viper、Zap 封装。不会因技能默认值改成其他日志或 Web 框架。

原始提交和许可证统一记录于 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)。分阶段功能、生成范围与验收统一记录于 [plan.md](../../plan.md)，不在本文件另维护任务清单。

## 备选与代价

| 备选 | 本次不采用的原因 | 当前选择的代价 |
| --- | --- | --- |
| GoFrame / HotGo | 更完整的工具与工程体系不是当前优先目标 | Nunu 需要补齐用户权限、字典和业务生成链路 |
| go-admin / Gin-Vue-Admin | 已有管理功能，但前端和生成约定与选定 Vben 存在适配工作 | Lambo 需要维护一套自己的 Vben 模板 |
| Go-zero / Kratos 微服务底座 | 当前没有独立发布或独立扩缩容的模块证据 | 首版以单体部署，后续按真实边界演进 |

## 依赖方向

Vben 页面通过 API 客户端访问 Go REST 接口；请求由 handler 进入 service，再调用 repository。状态流转、事务和授权条件由后端业务所有者执行，不能从 service 反向依赖 Gin 请求对象。公共工具不承载具体业务决策。

当前不增加 Redis、Kafka 或 Kubernetes。出现以下证据时重新评估：两个及以上实例确需共享会话或限流状态；至少两个模块需要独立发布并有独立扩缩容证据；持久任务积压或重试需求无法由现有数据库方案满足。引入前记录测量结果和具体依赖边界。

## 已知风险与验收边界

- Nunu Basic 导入提交较早、存在数据库和用户查询占位，不能直接声称已获得可用管理后台。
- Nunu 使用 Wire，上游维护状态及固定版本需要在 P0 复核；只在出现兼容或维护障碍时调整装配方式。
- Vben 保留上游多包结构，P0 决定并只维护一套业务应用；当前没有进行结构裁剪。
- UI 库、数据库、元数据真源、令牌存储方式及性能指标仍待确定，见计划中的待定表。
- 完成基线验收需要真实数据库、真实权限拒绝路径和浏览器业务闭环；本次导入没有执行这些验证。
